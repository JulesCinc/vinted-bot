# No retry, abort-on-block anti-bot resilience for Vinted polling

We treat any 403 from Vinted during a Pass as a hard stop, not something to retry ([#8](https://github.com/JulesCinc/vinted-bot/issues/8)). The research doc (resolving [#2](https://github.com/JulesCinc/vinted-bot/issues/2)) shows Vinted's blocking is rate/behavior-based with hours-long recovery, not a one-off fluke a few seconds' retry could out-wait — retrying into an already-flagged session risks extending the block rather than helping. On a 403, the bot aborts the rest of that day's Pass immediately: any GPU Model already checked before the block is still processed normally (Market Price Baseline computed, Alerts sent), but untried GPU Models are simply left for tomorrow's Pass, with no explicit retry, cap, or user-facing signal — the once-daily cadence ([ADR 0002](0002-local-scheduled-task-hosting.md)) is itself the retry mechanism, and a blocked Pass is treated exactly like ADR 0002's "machine was off" case: silent, naturally recovered on the next run. A single short-delay retry is still used for transient, non-block errors (timeout, connection reset, 5xx), since those carry no anti-bot signal. Session handling stays on `vinted_scraper`'s built-in automatic cookie acquisition — one fresh session per Pass, no cross-day persistence — and requests within a Pass are spaced with small randomized jitter. No explicit per-Pass request cap is introduced: even a generously long tracked list stays far under the observed ~20-requests-in-4-5-minutes blocking threshold at one request per GPU Model, once daily.

## Considered Options

- **Retry-with-backoff on 403** (rejected): the observed recovery time is hours, not seconds — an in-pass retry adds complexity without a realistic chance of succeeding before tomorrow's Pass would anyway, and risks compounding the block by adding more requests to an already rate-flagged session.
- **Skip just the blocked GPU Model and continue to the next** (rejected): the evidence points to session/IP-level blocking, not per-query blocking — continuing to send requests after a 403 is unlikely to succeed for the remaining models either, and does nothing but add more traffic to a session that's already flagged.
- **Surface a blocked Pass to Discord** (rejected): the bot's only output channel (Discord Alerts, [#7](https://github.com/JulesCinc/vinted-bot/issues/7)) is still unresolved on delivery mechanics, and a blocked Pass isn't actionable by the user anyway — it resolves itself on the next daily run, so it's handled the same as ADR 0002's silent missed-run case rather than adding a new alert type.
- **Persist the session cookie across daily runs** (rejected): saves at most one bootstrap request per day; not worth the added complexity of safely storing and expiring a cookie on disk, especially given ADR 0002's deliberate choice to keep the bot a stateless run-once script beyond the SQLite seen-set.
- **Explicit per-Pass request cap on tracked GPU Models** (rejected for now): current and foreseeable list sizes stay far under the observed blocking threshold at one request per model, once daily; revisit only if the list grows large enough to approach it.
